# ADR-0006. Канонический контракт результата распознавания (RecognitionResult v2)

Статус: принято (доработка после S13).
Контекст: решение заказчика о смене провайдера распознавания — вместо RD WEB
(markdown-экспорт) первый этап пойдёт через OpenRouter (VLM-модели) со
СТРУКТУРИРОВАННЫМ JSON на выходе. Алгоритмы проверки обязаны быть готовы к
этому заранее; сама интеграция с OpenRouter — отдельный этап и здесь не
решается. Связанные документы: ADR-0004, ADR-0005, `docs/RDWEB_IMPROVEMENTS.md`
(§3.3 — принятый в проекте стиль контракта structured-анализа).

## 1. Контракт живёт в отдельном пакете `@id/recognition`

`packages/recognition`: zod-схема (`schema.ts`), рендер канонического текста
(`render.ts`), legacy-адаптер (`adapters/rdweb-md.ts`), порт будущего источника
(`adapters/port.ts`, только типы). Зависимость пакета — только `zod`.

Не `@id/contracts`: контракт тянет за собой логику (рендер, адаптер), фронту он
не нужен, а `CONTRACTS_VERSION` версионируется как единое целое. Не `apps/api`:
`tools/fixtures` не имеет права зависеть от приложения (решение задокументировано
в `corpus-reference.ts`), а разбор legacy-формата нужен и корпусу, и проду.
Побочный эффект размещения: убит дубликат парсера markdown — `parseSourcePackage`
в `@id/fixtures` теперь обёртка над адаптером, и byte-идентичность текста
страниц доказана существующим golden-тестом эталонного корпуса.

## 2. Форма контракта: страницы → блоки, всё содержательное nullable

`recognition.result.v2` (v1 «по факту» — `schema_version: 1` их blocks.json).
Блок — discriminated union по `blockType`:

- `text` — `text` плюс необязательные `fragments` (paragraph / heading /
  table со структурированными ячейками — вместо GFM-текста) и `features`
  (рукопись/подписи/печати, троично: `null` — провайдер не смотрел);
- `image` — поля сегодняшнего md-рендера объектом: `imageType`, `axes`,
  `zone`, `level`, `summary`, `description`, `entities`, `verification`;
- `stamp` — поля штампа объектом: `code`, `stage`, `sheet`, `object`, `name`,
  `organization`, `revisions` + `extra` для незнакомых ключей. Сегодня строки
  `> **Stamp:**` ВЫРЕЗАЮТСЯ из текста как провенанс и поля штампа в портал не
  попадают вовсе — контракт закрывает этот пробел.

Обязательны только идентичность и провенанс (`schemaVersion`,
`source.provider/adapterVersion`, `workingPageIndex`, `blockType`). Геометрия
(`coordsNorm`, `ordinal`), уверенность и модель — nullable: RD WEB-адаптер не
умеет `fragments`, VLM-выход может не иметь геометрии. Оба укладываются без
насилия над схемой. Решение заказчика на сегодня: разметка блоков остаётся на
портале, на первых порах тип страницы указывает инженер вручную.

## 3. Канонический текст страницы версионирован

`renderPageText` + `PAGE_TEXT_RENDER_VERSION = 'recognition.page_text.v1'`.
Правила v1: пре-отрендеренный `page.text` возвращается дословно (legacy-путь —
байт-идентичность по построению); иначе сборка из блоков по `ordinal`
(text → как есть; image → фиксированный шаблон `**[IMAGE]** | …` +
`**Summary/Description/Entities/Verification**`; stamp → ничего), склейка
`\n\n`, схлопывание `\n{3,}`, `trim()`.

От этого текста зависят ВСЕ офсеты (цитаты классификации, `char_span`
реквизитов, доказательства замечаний). Любая смена правил рендера обязана
поднимать версию строки — инвариант тот же, что у `offset_convention`
в `page_text_versions` (миграция 0004); снапшот-тест в `render.test.ts`
делает нарушение громким.

## 4. §11 в контракте: запрещены подписанные ссылки на кропы, а не любые URL

`superRefine` схемы отклоняет строки с `…/api/crops/…` в любом поле. Запрещать
любой абсолютный URL нельзя: документы законно ссылаются на публичные реестры
и сайты производителей (проверено golden-прогоном: страница пакета кладки несёт
четыре такие ссылки в тексте сертификата ТЕХНОНИКОЛЬ).

## 5. Legacy-адаптер `rdweb-md.v1`

`canonicalFromArchiveEntries(markdown, blocksJson?)`. С blocks.json (корпус
`temp/MD`) — полный набор страниц с геометрией и stamp-блоками; без него
(форма архива job RD WEB) — только страницы и text/image-блоки из markdown.
Fail-closed правила выработаны на корпусе: страница markdown, которой нет в
blocks.json, — ошибка; страница с не-stamp блоками, отсутствующая в markdown, —
«экспорт усечён»; страница без блоков — законно пустая (в `temp/MD/new` таких
три). Ограничение: markdown не связывает строку `> **Stamp:**` с конкретным
stamp-блоком — поля раздаются stamp-блокам страницы по порядку (при одном
штампе на страницу — точно).

## 6. Что решается на этапе интеграции, а не здесь

- Канал OpenRouter: корпоративный шлюз proxy_llm (тогда §10-гвард
  `DIRECT_VENDOR_HOSTS` и CHECK-перечни `ai_runs` не меняются) либо иное
  решение заказчика.
- Постранично или по кропам блоков замороженной разметки; кто передаёт байты
  изображений. В типах порта байтов нет намеренно.
- Прод-запись canonical: артефакт вида `'canonical'`, конверт в
  `block_results.content_json`, колонка `render_version` в
  `page_text_versions` — обсуждены, отложены вместе с миграциями (enum «на
  вырост» без потребителя — ложное обещание в схеме).
- Включение полей штампа в канонический текст страницы (дало бы якорям сигнал
  «исполнительная схема», но требует перекалибровки якорей и новой версии
  рендера).
- Судьба artifact kind `blocks_json` (зарезервирован, не производится,
  P1-запрос к RD WEB в `docs/RDWEB_IMPROVEMENTS.md`): вероятно, сливается с
  будущим `'canonical'`.
- Требование к реализации порта: ответ, не прошедший валидацию по схеме,
  обязан отличаться от отказа модели — это разные исходы с разным поведением
  (стиль `docs/RDWEB_IMPROVEMENTS.md` §3.3).
- Перекалибровка якорей `@id/doc-types` на реальном VLM-выходе до боевого
  переключения (методика §16, leave-one-package-out).
