# ADR-0007. Распознавание через OpenRouter VLM по кропам блоков через proxy_llm

Дата: 2026-08-20. Статус: принято.

## Контекст

ADR-0006 зафиксировал канонический контракт результата (`recognition.result.v2`)
и намеренно оставил открытыми канал, гранулярность и формат ответа модели.
Заказчик закрыл эти вопросы (решения от 2026-08-20):

- канал — корпоративный шлюз **proxy_llm** (`PROXY_LLM_BASE_URL`); гвард §10
  `DIRECT_VENDOR_HOSTS` не ослабляется, прямых вызовов openrouter.ai нет;
- гранулярность — **кропы блоков замороженной разметки**: лист = одна задача,
  блок = один вызов модели со своим промптом по типу (text/image/stamp);
- ответ модели — **строго структурированный JSON для всех трёх типов блоков**.
  Это принципиальное отличие от RD WEB, который хранил markdown: результат
  предназначен для записи в БД, а не для чтения человеком;
- LM Studio порталу недоступен (другая машина) — OCR только через OpenRouter.

## Решение

### Канал и клиент

Отдельный порт `VlmPort` (`apps/api/src/llm/vlm-port.ts`) рядом с текстовым
`LlmPort`, а не расширение его: инвариант «текстовый порт принимает только
строки» остаётся выраженным типом, VLM-путь — санкционированное исключение §10
для стадии `recognize`, оформленное собственным типом с картинками.
`ProxyVlmProvider` шлёт `image_url` с data-URL base64 PNG и `response_format:
json_schema (strict)` — шлюз пропускает тело насквозь (проверено исходниками).
Политика (`LlmPolicy`: allowlist, месячный бюджет, rate limit) и журнал
`ai_runs` действуют и на VLM-вызовы; стадия `recognize` добавлена в CHECK
(миграция 0019), провайдер остаётся `proxy_llm`.

Контракт шлюза, учтённый клиентом: тело ≤ 26 MiB (предохранитель на нашей
стороне — 24 MiB и `LlmPayloadTooLargeError` с одним детерминированным
downscale-повтором), ответ ≤ 2 MiB (`upstream_response_too_large` не
повторяется), дедлайн 190 с (клиентский таймаут 240 с), `X-Idempotency-Key`
обязателен: `sha256(inputHash:model)`, стабилен между попытками одного вызова.
`finish_reason='length'` и пустой `content` — оплаченный неуспех, а не результат.
Поля `provider`/`plugins` шлюз вырезает, поэтому `require_parameters:true` и
`data_collection:"deny"` настраиваются оператором шлюза — это предусловие
эксплуатации, не код портала.

### Гранулярность и батчинг

Лист = задача `vlm.recognize_page {runId, pageIndex}`; блоки листа — строго
последовательные вызовы по одному кропу. Мультикартиночные батчи отвергнуты:
экономия — только повтор системного промпта, а цена — перепутанные ответы
между картинками, невозможность частичного повтора, риск ответа > 2 MiB и
идемпотентность «на группу» вместо «на блок». Параллелизм даёт очередь `llm`
(2–4), что согласовано с потолком одновременности шлюза (3 на клиента).

### Формат ответа

Все три типа блоков — строгий JSON (`json_schema`, `strict: true`, схемы без
`$ref`, `additionalProperties:false`, все поля в `required`, отсутствие
значения — `null`). Для text-блока схема зеркалит канонический
`ContentFragment` (paragraph/heading/table): маппинг «ответ → канон → БД»
почти тождественный, а `text`/`text_md` рендерятся детерминированно из
фрагментов (`render-fragments`, версия входит в `adapterVersion:
'openrouter-vlm.v2'`). Правила транскрипции переносятся из боевых промптов
RD WEB (кириллица/оси/ГОСТ, порядок чтения, `[неразборчиво]`); меняется только
формат вывода. Плейсхолдер `{DOC_NAME}` подставляется нейтральной строкой —
имена файлов заказчика в промпт не попадают.

Уточнение (`openrouter-vlm.v2`): «зеркалит» относится к смыслу полей, но не к
форме. Отправляемая схема text-блока ПЛОСКАЯ — один объект с обязательным
`kind` и nullable-полями остальных видов, — потому что Google AI Studio не
компилирует `anyOf` с разными наборами свойств и отвечает `400
INVALID_ARGUMENT` до генерации. Дискриминированный союз остаётся доменной
формой, в которую плоский ответ приводит нормализатор (`schemas.ts`).

Ответ, не прошедший схему после ремонта и одного корректирующего повтора, —
исход `invalid_response`; отказ модели (length/content_filter/пустой content) —
исход `model_refusal`. Это разные коды в `warnings` прогона (требование
ADR-0006), оба не повторяются сетью и оба оставляют блок непокрытым.

### Двухпроходная модель и публикация

Проход 1 — распознавание и верификация: `vlm.start_recognition` (гейт
`blocks_hash` замороженной разметки — замена сверки remote-хэшей: удалённой
стороны нет, доказывается неизменность собственной разметки) → N ×
`vlm.recognize_page` (checkpoint по `block_results`: UNIQUE
`(recognition_run_id, layout_block_id)` + `ON CONFLICT DO NOTHING`; прогресс —
таблица `recognition_run_pages`, не payload очереди) → `vlm.finalize_run`.
Финализация требует покрытия **всех** блоков всех трёх типов (строже
RD WEB-инварианта, допускавшего пустые stamp) и публикует одной транзакцией:
артефакт `canonical` (сериализованный `RecognitionResult`, три рубежа записи),
`page_text_versions` с `render_version`, перевод `current_block_result`,
`finishRun(done)`. Упавший или integrity-error прогон не публикует ничего.
Dry-run (`ai.dry_run_only`) выполняет всё, кроме публикации, — shadow-режим
для сравнения с RD-baseline до боевого включения.

Проход 2 — существующий анализ (`doc.classify_pages` → … → `checks.run`)
поверх опубликованных данных; он не изменился и запускается тем же событием
`recognition.export_stored`.

### Выбор ветки и матрица провайдеров

`recognition.provider` (`rdweb | openrouter_vlm`) и `recognition.vlm_model` —
`app_settings`; читаются роутом при постановке, фиксируются в
`settings_snapshot v2` и дальше не перечитываются: смена настройки действует
только на новые прогоны. Поддержанные комбинации с детекцией: rdweb+rdweb,
rdweb+VLM, local+VLM. Комбинация local-детекции с RD WEB OCR отвечает 409 с
диагностикой (у ревизии нет RD-документа); ленивое создание RD-документа —
осознанно отложено.

### Судьба blocks_json

Вид `blocks_json` остаётся зарезервированным и по-прежнему не производится:
его роль (машиночитаемая геометрия + результаты) целиком закрывает
`canonical`.

## Последствия

- Три рубежа идемпотентности (block_results → LRU-кэш → идемпотентный ключ
  шлюза) делают повтор задачи бесплатным; LRU не переживает рестарт — и не
  обязан, рубеж БД первичен.
- Корректирующий повтор — платный второй вызов; он выполняется не более одного
  раза и только по классифицированной исправимой причине.
- Промпты живут в governance `prompt_templates` (стадия `recognize`, сиды в
  состоянии draft) — прогон без опубликованных промптов отказывает с внятным
  текстом, публикация — действие администратора.
- Боевое включение — только после shadow-прогонов на корпусе `temp/MD`,
  сравнения с RD-baseline и перекалибровки якорей `@id/doc-types`
  (методика §16, leave-one-package-out) — условие ADR-0006 сохраняется.
- Предусловия эксплуатации: клиент шлюза (токен, allowlist по egress-IP,
  `allowedModels:["*"]`, желателен отдельный ключ OpenRouter), version-pinned
  модель с поддержкой image input и structured outputs в
  `LLM_MODEL_ALLOWLIST`.
