# ADR-0005. Распознавание, экспорт и цикл сверки RD WEB: допущения и основания

Статус: принято (S7).
Контекст: §5.2 (шаги 5–9), §6.2, §3.5, §12 (задачи 10–13) плана v5; ADR-0004.

Все решения приняты по прямому чтению исходников RD WEB
(`temp/RDNEW/services/web_ocr/`), а не по их документации: `docs/DEPLOYMENT.md`
у них описывает эндпоинты, которых не существует (пункт техзадания S13).

## 1. Пути запуска и опроса — с префиксом `/api/recognition`

`recognition.py` подключает роутер как `APIRouter(prefix="/api/recognition")`, и
`recognition_jobs.py` объявляет внутри него `POST /jobs` и `GET /jobs/{job_id}`.
Код S6 обращался к `/api/jobs` — на настоящем сервере это 404.

**Решение.** `startRecognition` → `POST /api/recognition/jobs`,
`pollRecognition` → `GET /api/recognition/jobs/{job_id}`.

## 2. Запуск OCR невозможен без выбора модели

`JobCreateRequest.settings` — `dict[BlockType, BlockTypeSelection]`, а у
`BlockTypeSelection` (`api/services/recognition.py`) обязательны `provider_type`
и `model_id`; `model_config = ConfigDict(extra="forbid")`. Пустой `settings`
отвергается валидатором модели. То есть «запустить с настройками по умолчанию»
у их контракта нет как понятия.

**Решение.** Выбор приходит из конфигурации портала: `RDWEB_OCR_MODEL`
(обязателен для запуска), `RDWEB_OCR_PROVIDER` (по умолчанию `lmstudio` —
единственное значение их `ProviderType`, кроме `manual`) и необязательный
`RDWEB_OCR_PROMPT_PROFILES` вида `text=<id>,image=<id>,stamp=<id>`. Значения по
умолчанию для модели нет намеренно: выдуманный `model_id` чужой системы дал бы
422 из RD WEB вместо внятного «не настроено» в консоли задач. Промты OCR портал
не редактирует (§10) — он выбирает профиль, а профиль принадлежит их админке.

`scope` запускается как `all`: набор блоков уже сведён циклом сверки, а
`unrecognized` означал бы результат, собранный из двух разных запусков.

`document_mode` выключен: в этом режиме в job уходят ТОЛЬКО TEXT-блоки, а
штамп подавляется в выходных файлах (`partition_document_mode`,
`finalizer/render_*`). §5.3 прямо опирается на `image`- и `stamp`-блоки, поэтому
включение режима выбросило бы часть заказанного набора уже на их стороне — при
совпавших хэшах.

## 3. Канонический порядок чтения — ПЛОТНЫЙ РАНГ, а не сырой `sort_order`

Это исправление дефекта, который сделал бы §5.2 неисполнимым.

`sort_order` на удалённой стороне назначает ИХ сервер: `_next_sort_order` даёт
`max+1` внутри группы «страница × тип», `PATCH` его не трогает вовсе, а из
запроса он не принимается ни в create, ни в update. Наш `sort_order` живёт по
своим правилам. После любого удаления в группе остаются дыры (0, 5, 7). Сырые
числа двух сторон не совпали бы никогда, и `remote_layout_hash_before` не
совпал бы с `blocks_hash` НА ИСПРАВНОМ ПРОГОНЕ — то есть `integrity_error`
перестал бы что-либо означать.

**Решение.** `computeBlocksHash()` подставляет в каноническую строку плотный
ранг блока внутри группы «страница × тип» (сортировка по `sort_order`, тай-брейк
по канонической геометрии — идентификаторы у сторон разные). `BLOCKS_HASH_VERSION`
поднят до 2. Хэш по-прежнему ловит ПЕРЕСТАНОВКУ блоков и перестаёт ловить разрыв
нумерации, при котором порядок чтения тот же. Ось группировки взята той же, что
у них, — иначе привести порядок к нужному было бы нечем.

## 4. Сверка идёт группами, а не поблочно

Из пункта 3 следует, что управлять удалённым порядком можно только
последовательностью операций внутри группы. Поэтому `reconcileLayout` проходит по
каждой группе «страница × тип» целиком:

- совпадающие позиции не трогаются вовсе (`PATCH` сбрасывает `status` и
  `active_result_id` — переписывать неизменившуюся геометрию значило бы
  обнулять результаты прошлого прогона на ровном месте);
- расходящиеся приводятся `PATCH`'ем с `expected_version` (их `sort_order`
  остаётся прежним, значит и ранг тоже);
- хвост удалённой группы удаляется с `expected_version`;
- хвост нашей группы создаётся в порядке возрастания — их сервер выдаёт `max+1`,
  то есть дописывает ровно в конец и ровно в нашем порядке.

После такого прохода плотный ранг совпадает по построению. Частичный сбой
безопасен: следующий проход перечитывает удалённый набор и доводит его до того
же состояния; операции «продолжить с середины» здесь нет.

## 5. Экспорт job'а содержит ТРИ записи, и `blocks_json` среди них нет

`exports.download_job_zip` собирает архив из `document.md`, `document.html` и
`qa_manifest.json`. Машиночитаемый индекс блоков (`{stem}_blocks.json`,
`finalizer/blocks_json.py`) есть только в ПОДОКУМЕНТНОМ архиве
(`exports.download_document_zip`), который дополнительно кладёт внутрь ИСХОДНЫЙ
PDF — то есть второй заезд 86 МБ ради геометрии, которая у нас заморожена.

**Решение.** Забирается архив job'а. Виды артефактов (§3.5) производятся такие:
`zip` (архив целиком), `md`, `html`, `qa`. Вид `blocks_json` на легаси-API НЕ
производится — это зафиксированное допущение, а не пропуск. Требование положить
индекс блоков в архив job'а — пункт техзадания S13.

## 6. `model_id` и `confidence` читаются отдельным read-back

В архиве их нет вовсе, а §9.1 прямо требует, чтобы низкая уверенность OCR не
давала `fail`. Единственный источник — `GET /api/blocks/{id}/results`
(`blocks_history.list_block_results`), отдающий историю результатов блока с
отметкой активного.

**Решение.** Порт объявляет `fetchBlockResults(blockIds)` во множественном числе:
сегодня это N обращений (bulk-ручки у них нет), завтра — один вызов, и меняется
реализация, а не вызывающий. Это НЕ второй экспорт: артефакт забирается один раз,
а провенанс дочитывается после него. Недоступность read-back не роняет прогон:
текст блока остаётся верным, а `model_id`/`confidence` честно пустыми.

**Долг S13.** Bulk-чтение активных результатов документа одним запросом.

## 7. `has_export` терминального job'а — это окончательный ответ

`JobOut.has_export = bool(job.qa_manifest_s3_key)`. Порядок записи в их
финализаторе (`finalizer/service_export._export`) фиксированный: манифест
выкладывается в хранилище → проставляется `qa_manifest_s3_key` → пересчитываются
счётчики → и только последним пишется терминальный статус job'а. Значит `done`
при `has_export=false` означает не «подождите», а «манифеста не будет»; стадия
«идёт сборка» выражена у них отдельным НЕтерминальным статусом `finalizing`.

**Решение.** Терминальный успех без `has_export` немедленно переводит прогон в
`failed` с причиной, а не расходует шестьдесят попыток поллинга ради
предрешённого исхода. `completed_with_warnings` считается успехом (документ
собран, перечень неисполнимых блоков лежит в QA-манифесте), `paused` —
нетерминальным (job можно возобновить).

## 8. Забор экспорта однократен тремя рубежами

Их экспорт ТРАНЗИЕНТНЫЙ: архив собирается на лету из ТЕКУЩИХ активных
результатов блоков, материализован только QA-манифест. Значит «тот же архив
завтра» их API не обещает, и второй забор — это, возможно, другие байты.

**Решение.** Перед обращением к RD WEB проверяются по порядку:

1. строка `artifact_versions` вида `zip` (UNIQUE по прогону и виду) — забор уже
   был, байты обязаны лежать у нас, и их хэш сверяется с записанным;
2. объект в нашем хранилище по детерминированному ключу `artifacts/{runId}/zip.zip`
   — забор был, но строку записать не успели: байты берутся оттуда;
3. и только теперь `GET /api/exports/jobs/{id}/zip`.

Без второго рубежа падение между выкладкой и записью строки означало бы второй
забор транзиентного экспорта. Однократность при этом держится не аккуратностью
обработчика, а ограничением БД и детерминированным ключом объекта.

## 9. Подписанные ссылки на кропы: хранение побайтовое, ВЫДАЧА санируется

`render_markdown` печатает у каждого TEXT/IMAGE-блока строку
`> **Crop:** [Crop](<url>)`, где url — БЕССРОЧНАЯ подписанная ссылка «формата
сайта» (`export_crop_short_url`). §11 относит подписанный URL к значениям,
подлежащим redaction, а `page_text_versions.text_md` живёт в БД без срока
хранения и уезжает в ответы API и в цитаты доказательств.

Ссылка эта — не косметика, а **bearer-возможность**: отдача кропа у них
публичная (`api/routes/crops.py` подключён без зависимости аутентификации,
`app.py`), срока действия у подписи нет. Попав в историю браузера, в
пересланный файл или в лог прокси, такой URL даёт чтение изображения фрагмента
чужой исполнительной документации в обход их RBAC и навсегда.

**Решение, часть 1 (разбор).** При разборе `document.md` строки провенанса
`> **Created:**`, `> **Crop:**` и `> **Stamp:**` в текст страницы и в результат
блока не попадают, а любая уцелевшая абсолютная ссылка обезвреживается. Строка
`> status: …` остаётся: это диагностика результата, а не провенанс.

**Решение, часть 2 (выдача) — правка S7-ревизии.** Вырезания из `text_md` было
НЕДОСТАТОЧНО. Те же ссылки приезжают ещё в трёх местах: в `document.html`
(`render_html.py` печатает `<div class="block-crop">…<a href="…">`), в самом
архиве и — по открытой схеме `QaManifest` (`extra="allow"`, свободный
`checks: dict`, `domain/results.py`) — потенциально в `qa_manifest.json`. Все
четыре вида артефактов отдавались наружу маршрутом
`GET /api/v1/recognition-runs/:runId/artifacts/:kind/content` побайтово, то есть
дыра была закрыта ровно в одном из четырёх мест.

Поэтому:

- производные виды (`md`, `html`, `qa`, `blocks_json`) на выдаче проходят через
  `redactArtifactContent()`. Правило у каждого носителя своё — из markdown
  выбрасываются строки провенанса, из html вырезается бокс ссылки, json
  обходится деревом и пересобирается (текстовая замена по сырому JSON испортила
  бы экранирование, а получатель обязан иметь возможность его разобрать), — но
  последний рубеж общий: абсолютных ссылок в ответе не остаётся;
- в ответ добавлены `x-artifact-content-sha256` (хэш ОТДАННЫХ байт) и
  `x-artifact-redacted`. `x-artifact-sha256` при этом продолжает описывать
  ХРАНИМЫЙ артефакт — без второго заголовка получатель считал бы, что тело не
  сошлось с заявленным хэшем;
- список артефактов с хэшами и размерами доступен как раньше: ссылок он не
  содержит.

**Почему хранение НЕ санируется, а выдача санируется.** Это два разных вопроса.
`artifact_sha256` — доказательство того, ЧТО мы получили от RD WEB (§1.6,
«верификация artifact hash»); санировав байты перед записью, мы записали бы хэш
того, что произвели САМИ, и не смогли бы ни доказать полученное, ни сверить
повторный заход с записанным (п. 8 выше опирается ровно на это). Санация же
нужна не хранилищу, а получателю: секрет опасен там, где он покидает периметр.
Отсюда единственная непротиворечивая конструкция — неизменяемый архив внутри и
санированная копия наружу.

**Сырой `zip` наружу не отдаётся подрядчику.** Санировать его нельзя (см. выше),
а отдавать побайтово — значит отдавать все ссылки сразу. Выбран вариант
«закрыть правом», а не «не отдавать вовсе»: архив остаётся доказательством, и
доступ к нему нужен на разборе инцидента. Маршрут требует `diagnostics.read`
(только `admin`, §4.1) — то же право, что у консоли задач и экрана диагностики
(§11). Подрядчику и инженеру он отвечает 403; текст, ради которого артефакты и
запрашиваются, они получают видами `md`/`html`/`qa`.

**Двойник обязан быть не мягче оригинала.** `tools/fake-rdweb` не выводил
`crop_url` в html вовсе, поэтому утечка через `html` и `qa` не ловилась ни одним
тестом — двойник проверял отсутствие того, чего и не приходило. Приведён к
поведению оригинала: ссылка кладётся во все три записи архива.

## 10. Сопоставление блоков — по канонической геометрии и рангу

Идентификатор блока на их стороне нам заранее неизвестен, `client_id` они
возвращают только в ответе на create и нигде не хранят, а таблица связей
разъехалась бы с фактом при первом же пересоздании блоков циклом сверки.

**Решение.** На момент забора экспорта хэши уже совпали ДО старта OCR и не
изменились ПОСЛЕ, то есть мультимножества блоков двух сторон равны.
Сопоставление по той же канонической форме — следствие уже проверенного
равенства, а не эвристика. Несопоставленный локальный блок при совпавших хэшах
означает расхождение канонизации и сопоставления, то есть дефект НАШЕЙ стороны, и
останавливает прогон.

## 11. Закрытие RD-документа — долг S6, закрытый здесь

`closeRunDocument()` в порту проверяет достижимость документа и не более того:
настоящей операции закрытия у RD WEB нет (ADR-0004 §7). Факт закрытия
фиксируется у нас — `rd_run_documents.closed_at`, — и с этого момента
`startRecognitionRun` отказывает в новом прогоне по той же разметке.

Закрытие выполняется в двух случаях: после успешного забора экспорта (§5.2,
шаг 9) и при `integrity_error` из-за подмены набора блоков — документ больше не
описывает заказанное, и повторный прогон по нему был бы прогоном по
подменённому набору. При инфраструктурном отказе (`failed`) документ остаётся
открытым: повтор по той же замороженной разметке правомерен.

Проба достижимости — диагностика, а не условие: недоступность их API не должна
оставлять документ формально открытым для следующего прогона.

## 12. Идемпотентность запуска — доменная, заголовок вторым рубежом

`Idempotency-Key` обязателен на `POST /revisions/{id}/recognize` (§14) и входит
в ключ дедупликации задачи. Но первый рубеж — доменный инвариант: незавершённый
прогон по ревизии разметки один, и повторный запрос возвращает его же. После
успешного прогона RD-документ закрыт, и новый прогон требует новой ревизии
разметки; после инфраструктурного отказа повтор по той же разметке разрешён.

Отдельной таблицы ключей идемпотентности не заводится: она была бы вторым
источником правды о том, что уже сделано, а первый (`recognition_runs` плюс
`closed_at`) и так неизбежен.

## 13. Исчерпание попыток ЛЮБОЙ задачи прогона завершает прогон

Правка S7-ревизии. `JobRunner` при исчерпании попыток помечает задачу `dead` и
`recognition_runs` не трогает — он о прогонах не знает и знать не должен.
Значит закрывать прогон обязан слой задач распознавания. Он это делал, но
перечислением: обрабатывался `ZipError`, а `ExportFormatError`,
`RecognitionIntegrityError` и обычный `Error` оставляли прогон в `running`
навсегда. Прогоном показано шесть таких путей у одной только задачи 13.

Последствие тяжелее, чем «поле не обновилось». `startRecognitionRun` на
незавершённом прогоне возвращает его же (`created: false`), а RD-документ
остаётся открытым: новый прогон по этой ревизии разметки невозможен, ревизия
запирается насмерть, и при этом цепочка задач продолжает крутиться по кругу.

**Решение.** Общее правило вместо перечисления: обёртка `withRunTermination`
поверх всех четырёх обработчиков. Условие срабатывания то же, по которому
`JobRunner` объявляет задачу мёртвой, — последняя попытка либо неповторяемая
ошибка (`classifyFailure().permanent`); на не последней попытке прогон остаётся
`running`, потому что повтор ещё предстоит. `RecognitionIntegrityError` даёт
`integrity_error` (расхождение доказательств), всё остальное — `failed`.
Точные диагнозы внутри обработчиков остаются: они закрывают прогон раньше и с
внятной причиной, а обёртка — это сеть под ними, а не замена им.

Причина проходит через ту же redaction, что и текст страниц, и обрезается по
длине: она уходит в `revision_events` и в ответ API, а дословный дамп чужого
ответа в поле, которое читает подрядчик, — это утечка, а не диагностика.
Подробная диагностика лежит в `job_runs.error_message` и `error_events` (§11).

## 14. Нулевой и неполный экспорт не считается успешным прогоном

Правка S7-ревизии. Пустой `document.md` давал `done` с нулём страниц и нулём
результатов; архив без единого блока — тоже `done`; лишние секции блоков молча
отбрасывались `flatMap`'ом; страница с номером вне рабочего документа уходила в
общий `pagesSkipped`, неотличимо от «уже записана». То есть прогон, распознавший
ноль, был неотличим от успешного — после самой дорогой стадии конвейера, ради
которой пользователь и ждёт текст.

**Какое покрытие обязано быть.** Рубеж взят не произвольный: это ИХ собственный
QA-инвариант. `finalizer/service_export._export` считает
`terminal_ids = [b for b in ordered if b.block_type != STAMP]` и проверяет
`markdown_contains_all_blocks = all(bid in md for bid in terminal_ids)`. Значит
`document.md` обязан содержать секцию КАЖДОГО не-STAMP блока задания — включая
блоки, у которых OCR не получился: их рендер выводит секцию с категорией и
причиной. STAMP — единственный законный допуск: `iter_markdown_blocks`
пропускает его при обходе, собственной секции такой блок не имеет.

**Решение.**

| Наблюдение                                            | Исход                                                    | Почему так                                                                                                                                                           |
| ----------------------------------------------------- | -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| секция блока, не принадлежащего замороженной разметке | `integrity_error`                                        | хэши совпали ⇒ мультимножества блоков равны; чужая секция означает, что экспорт описывает НЕ тот набор                                                               |
| покрыто меньше не-STAMP блоков, чем заморожено        | `failed`                                                 | доказательства не разошлись, но результата нет; счётчики `blocksExpected`/`blocksCovered`/`blocksMissing` и предупреждение `export_incomplete` показывают, насколько |
| ноль страниц либо ноль ожидаемых блоков               | `failed`                                                 | нулевой результат — не успех                                                                                                                                         |
| `## Page N` вне рабочего документа                    | `integrity_error`                                        | экспорт описывает документ, которого мы не заказывали; отдельная причина и отдельный счётчик `pagesOutOfRange`, а не общий «пропущено»                               |
| секция есть, тело пустое                              | `done` + `blocksWithoutText` в `counts` и предупреждение | §9.1 прямо требует, чтобы низкое качество OCR не давало `fail`                                                                                                       |

Проверка покрытия стоит ДО записи результатов, а батч со страницей вне диапазона
не пишется вовсе: прогон, который сейчас будет остановлен, не имеет права
оставить за собой половину неизменяемого текста страниц.

Счётчики `saveRecognitionResults` разведены по причинам
(`pagesAlreadyPresent`/`pagesOutOfRange`, `blocksAlreadyPresent`/`blocksUnknown`)
именно потому, что «штатный повтор задачи» и «экспорт описывает не тот документ»
складывались в одно число и второе было неотличимо от первого.
