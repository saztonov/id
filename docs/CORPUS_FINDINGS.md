# Проверенные факты о корпусе

Факты, установленные прямой проверкой файлов, а не предположением. На них опираются
тесты и правила, поэтому каждый пункт содержит способ перепроверки.

Корпус — два раздела работ (2.5.1 «Кровля автостоянки», 2.1.5 «Несущие ЖБ конструкции
надземной части»), 142 страницы, три комплекта. Разделов в реальности больше, поэтому
любые выводы ниже относятся только к этим двум.

---

## Криптографических подписей в PDF нет

Все три исходных PDF: `ByteRange` — нет, `SubFilter` — нет, `/Type/Sig` — 0, `/FT/Sig` — 0,
`startxref` — 1, `%%EOF` — 1, `/Encrypt` — 0. Формат PDF-1.6 с объектными потоками
(`ObjStm` 2–6), сканы внутри как `DCTDecode`/`JPXDecode`.

Решающее доказательство — отсутствие `ByteRange` и `SubFilter`: словарь подписи не может
находиться внутри `ObjStm`, потому что `ByteRange` адресует байтовые смещения самого файла.
Единственный `%%EOF` — подтверждающий признак: подпись всегда накладывается инкрементальным
обновлением и даёт как минимум второй `%%EOF`.

**Следствие.** Штамп «ДОКУМЕНТ ПОДПИСАН ЭЛЕКТРОННОЙ ПОДПИСЬЮ / Сертификат: … / Владелец: …»
— растровая печать системы ЭДО, впечатанная в изображение страницы. Проверяется только по
OCR-тексту, поэтому правило `SIG.STAMP.370` имеет severity `warning`, а не `error`.
Полная криптографическая проверка в MVP не реализуется; структурный детектор возвращает
`none_detected` на всём наблюдаемом корпусе.

## Контрольные суммы ИНН и ОГРН

Алгоритмы проверены на реальных значениях из актов.

**ИНН — все десять валидны**: 7709574093, 7736255508, 7725825428, 7702521529, 6229024796,
7720961314, 7728093677, 6646009256, 4003033040, 7724484743. Веса подтверждены:
10-значный — `[2,4,10,3,5,9,4,6,8]`; 12-значный — `[7,2,4,10,3,5,9,4,6,8]` и
`[3,7,2,4,10,3,5,9,4,6,8]`, обе цифры по модулю 11, затем 10.

**ОГРН — пять из семи валидны**: 1047796801920, 5157746024662, 1147746393453,
1097799011859, 1267700005210. Контрольная цифра 13-значного — остаток от деления первых
12 цифр на 11, взятый по модулю 10; 15-значного — первых 14 цифр на 13, затем по модулю 10.

Два значения не проходят проверку, и это **два принципиально разных случая**:

| Значение                     | Что не так                                             | Как обязано отработать правило                      |
| ---------------------------- | ------------------------------------------------------ | --------------------------------------------------- |
| `124770050762` (ООО «МС-90») | 12 цифр вместо 13                                      | `fail` — дефект оформления документа                |
| `1067746138138` (ООО «МСЕТ») | 13 цифр, контрольная не сходится: ожидалась 0, стоит 8 | `undetermined` — дефект распознавания, не документа |

Второй случай — прямое обоснование троичной логики. Значение вычитано с круглой печати,
перекрытой рукописной подписью; тот же OCR прочитал в этой печати само слово «ОГРН» как
«ОТРИ». Правило `AOSR.HDR.022`, поднявшее бы здесь `error`, выдало бы ложное обвинение
подрядчику в подделке реквизитов. Порог уверенности OCR обязан переводить такой результат
в «требуется ручная проверка».

Оба значения входят в регрессионный набор: первое обязано давать `fail`, второе — `undetermined`.

## Что подтверждено в API RD WEB

- `full-page-text` **удаляет существующие блоки страницы** — из докстринга `blocks_bulk.py`:
  «обвести каждую страницу одним TEXT-блоком (прежние блоки страницы удаляются)».
- **Версионирования `/api/v1` нет**, все роуты на `/api/...`.
- **M2M-аутентификации нет**; совпадения по `api_key` относятся к настройке endpoint'ов
  LM Studio, а не к аутентификации клиента.
- **У async-детекции нет REST-статуса.** `DetectBlocksResponse.detect_job_id` описан как
  «id фоновой detect-задачи (для отслеживания прогресса)», но роута опроса не существует;
  прогресс идёт только по WebSocket, рассчитанному на UI.
- **Синхронная детекция принимает `page_indices: list[int] | None`** и возвращает
  `created: list[BlockOut]` прямо в ответе. Это делает её единственным пригодным режимом
  для headless-интеграции.
- **`BlockOut` не содержит ни `confidence`, ни `model_id`.** Единственное поле `confidence`
  принадлежит `BlockResultOut` и относится к OCR, а не к детектору. Провенанс детектора
  в легаси-режиме недоступен и не должен выдумываться.

## Реестр приложений называет документы не так, как они называются сами

Прямое следствие для методики сверки, отменяющее часть исходного замысла.

| Строка реестра                     | Фактический заголовок листа        |
| ---------------------------------- | ---------------------------------- |
| «Паспорт качества Арматура №16005» | «СЕРТИФИКАТ КАЧЕСТВА № 16005»      |
| «Паспорт …№230126/2/126000477.1.1» | «Паспорт № 230126/2/126000477.1.1» |

В файле 01-ДК2-СЦ реестр называет **все двенадцать** документов о качестве просто
«Документ о качестве», и лишь один — «Документ о качестве бетонной смеси», хотя формы
у трёх поставщиков разные.

**Сверять комплект с реестром по виду документа нельзя — только по номеру.** Вид из
реестра пригоден как слабая подсказка для классификатора, но расхождение вида само по
себе не является дефектом комплекта: подрядчик заполняет реестр от руки и обобщает.
Это корректирует §8.3 плана, где реестр назван эталонной разметкой: эталонен он по
составу и номерам, но не по видам.

## Замер полноты якорей на корпусе

158 блоков трёх комплектов, прогон против 68 типов каталога.

| Метрика                                            | Значение |
| -------------------------------------------------- | -------- |
| Без единого совпадения, окно заголовка 3 строки    | 78 (49%) |
| Без единого совпадения при сканировании всего тела | 37 (23%) |
| С двумя и более типами одновременно                | 18       |
| АОСР пойман                                        | 0 из 3   |

Пять системных причин, каждая исправлена в `matching.ts` и каталоге:

1. **Markdown-префиксы убивали якоря с `^`.** OCR печатает `##### АКТ`, `##### ЗАКЛЮЧЕНИЕ`,
   `##### Паспорт № …`; шаблон `^\s*` через `#` не проходит. Мертвы были 11 из 16
   привязанных к началу строки якорей.
2. **Якорь не отличал заголовок от упоминания.** Строка реестра
   `| 13 | Документ о качестве; Раствор М-150 | …` взводила тип, а страница реестра
   целиком давала пять-шесть типов. Паспорт РОКВУЛ типизировался как сертификат плюс
   декларация — по собственному подвалу «Продукция сертифицирована…».
3. **Печатная подсказка бланка АОСР давала два ложных типа на каждом акте.** Текст формы
   РД-11-02 «(исполнительные схемы и чертежи, результаты экспертизы…)» → `exec_scheme`,
   строка «Приложения: Реестр приложений №1» → `annex_registry`. Воспроизводится на 100%.
4. **`exec_scheme` не срабатывал ни на одной настоящей схеме.** Четыре листа исполнительных
   схем не содержат слов «исполнительная схема» ни в тексте, ни в штампе. Текстом этот тип
   не определяется в принципе — его должен присваивать классификатор по составу блоков
   страницы (наличие `image` и `stamp`).
5. **Штамп ЭП печатается в подвале содержательных страниц**, а не только на отдельных
   листах. Роль `signature_visual` с `autoAttach: true` присоединяла бы настоящий документ
   к предыдущему как служебный лист — прямая потеря документа.

Надёжно работали и до ремонта: `mill_certificate` 16/16, `lab_protocol_concrete` 5/5,
`declaration` 4/4, `copy_stamp` 49/49.

### После ремонта

Повторный замер тем же способом, но через `matchDocTypes` из `matching.ts`:

| Контрольная точка                      | До       | После        |
| -------------------------------------- | -------- | ------------ |
| АОСР пойман                            | 0 из 3   | **3 из 3**   |
| «КОПИЯ ВЕРНА»                          | 49 из 49 | **56 из 56** |
| Блоков с двумя и более типами          | 18       | **0**        |
| Ложных `exec_scheme`                   | 2        | **0**        |
| `annex_registry` ложных (стр. 2 актов) | 2        | **0**        |
| Документы о качестве                   | 8 из 11  | **11 из 11** |

Реальная база «КОПИЯ ВЕРНА» оказалась 56, а не 49: к 53 листам с текстом одной строкой
добавились три, где OCR разорвал надпись на «КОПИЯ» и «ВЕРНА».

Цифра «без единого типа» выросла с 37 до 102 из 158, и это не регресс, а смена смысла
метрики. Прежний матчинг подстрокой по всему телу засчитывал любое упоминание, давая
и совпадения, и мусор. Сейчас из 102 блоков 67 имеют роль страницы (56 `copy_stamp`,
7 `signature_visual`, 6 `annex_continuation`, 5 `doc_continuation`), и совсем без сигнала
остаются 35.

### Что осталось нерешённым и почему это задача S8

Четыре класса документов текстом не определяются в принципе:

1. **Исполнительные схемы, 0 из 4.** Слов «исполнительная схема» нет ни в тексте, ни в
   штампе; страница состоит из `image`-блока и легенды. Определяется только по составу
   блоков страницы.
2. **Продолжения многостраничных документов без маркера.** Вторые страницы актов,
   11 страниц тела технического заключения, продолжение таблицы реестра без шапки.
   Явного «Лист N из M» там нет — нужен структурный признак.
3. **Технический паспорт МСЕТ.** Страница отдана единственным `image`-блоком, весь текст
   живёт в описании графики, а не в тексте страницы.
4. **Заголовок, разорванный OCR на две строки** («СЕРТИФИКАТ» / «СООТВЕТСТВИЯ» на стр. 45).
   Построчный якорь такое не ловит.

Первые три требуют метаданных страницы, которых у якорей нет по определению. Четвёртый
решается склейкой соседних коротких строк в зоне заголовка — это правка матчера, но её
цена (риск склеить заголовок с соседним текстом) требует замера, поэтому она отложена
в S8 вместе с остальными.

**Вывод для плана.** Оценка «детерминированные правила закрывают 70–80% страниц» (§8.2)
измерением не подтверждается. Реально якоря дают тип 56 блокам из 158 (35%), ещё 67 —
роль страницы; 35 блоков остаются без сигнала. Долю следует пересчитать после S8, когда
появится классификация по составу блоков.

## Особенности среды

- `jsonb_matches_schema()` в PostgreSQL отсутствует: это функция расширения `pg_jsonschema`,
  которое стандарт не разрешает. Валидация геометрии полигонов делается нормализованной
  таблицей с обычными `CHECK`.
- `pg_trgm.similarity('РОСС RU Д-RU.PA01', 'РОСС RU Д-РУ.РА01')` = **0.55**. Это одна и та же
  декларация, набранная в двух алфавитах. Без фолдинга гомоглифов сверка с реестром
  не работает: пороги similarity такое расхождение не закрывают.
