# Приём готовых кропов в RD WEB: требования интегратора

Документ адресован команде, сопровождающей и дорабатывающей RD WEB. Он описывает четырнадцать
изменений, необходимых для того, чтобы RD WEB распознавал растры блоков, **нарезанные снаружи**, —
каждое с фактическим состоянием, ценой этого состояния для интегратора, предлагаемым изменением и
критерием приёмки.

Интегратор — портал «Исполнительная документация» (ИД). Сегодня он загружает в RD WEB рабочий PDF,
синхронизирует набор блоков и запускает распознавание документа целиком; этот путь остаётся и описан
в `docs/RDWEB_IMPROVEMENTS.md`. Новый путь другой: портал сам размечает страницу, сам режет и
разворачивает растр блока и присылает **готовую картинку** с манифестом. RD WEB в нём — исполнитель
распознавания, а не владелец документа.

Причина смены пути — не удобство. Портал перешёл на разметку по формату листа: лист A4 и мельче
распознаётся ОДНИМ полностраничным блоком, на крупном листе размечается только штамп и зона номера
листа. Решение «что распознавать» принимает стадия разметки портала и никто больше. Отдавать RD WEB
PDF ради того, чтобы он повторно нарезал уже нарезанное, значит завести второй источник геометрии и
второе место, где картинка может разойтись с той, по которой портал ведёт сверку.

**Ключевое следствие для принимающей команды.** Это не «одна ручка и одна вью». Конвейер RD WEB
сегодня безусловно грузит документ и режет кроп сам
(`services/web_ocr/pipeline/processor_prepare.py:67`, `:155`), а происхождение растра строит из
собственных байтов (`services/web_ocr/pipeline/lineage_record.py:93`). Внешний кроп — **новая ветка
исполнения** в подготовке вызова, и пункт 6 её не прячет.

## Как читать этот документ

**Каждый пункт устроен одинаково.** _Сейчас_ — фактическое поведение со ссылкой на файл RD WEB.
_Цена_ — что интегратору приходится делать или чем он рискует из-за этого поведения. _Требуется_ —
что должно измениться. _Приёмка_ — проверяемое условие, по которому пункт считается закрытым.

**Всё в разделе «Сейчас» проверено прямым чтением исходников** RD WEB — не по памяти, не по
документации и не по прошлому документу. Ссылки даны в виде `путь:строка` от корня репозитория RD
WEB. Там, где факт по исходникам установить не удалось, стоит явная пометка, а вопрос вынесен в
раздел 7 — таких мест намеренно не скрыто ни одного.

**Численные оценки приведены только измеренные.** Все — на эталонном комплекте ИД «Мастер апрель
2026»: 220 страниц (208 × A4, 12 × A3 альбом), 112 МиБ. Оценка пропускной способности взята из
заявленной командой RD WEB производительности узла (20 блоков/мин, A4 в четыре потока). Сроков и
трудозатрат документ не оценивает — это предмет планирования принимающей команды.

## 2. Что НЕ меняется (пункт 0)

Перечислено, чтобы у принимающей команды был точный список того, что новый путь **не** затрагивает, и
чтобы каждое требование ниже читалось на этом фоне.

- **Схемы результатов.** `StampBlockResult` (`services/web_ocr/domain/results.py:148-178`) остаётся
  поле-в-поле таким, как есть. Портал НЕ просит добавить в него номер листа: ячейка номера лежит вне
  прямоугольника штампа, механизма дозапроса кропа у RD WEB нет, и поле было бы `null` всегда. Портал
  добывает номер геометрией на своей стороне — отдельным блоком «зона номера», который приезжает
  обычным `text`-кропом.
- **Промпты, промпт-профили и модели.** Ни текст, ни версии, ни выбор моделей по типам блоков не
  затрагиваются. Внешний кроп идёт в те же `selections` job'а, что и внутренний
  (`services/web_ocr/api/services/recognition.py:354`).
- **Существующий путь «документ → детекция → job».** Легаси-интеграция портала
  (`docs/RDWEB_IMPROVEMENTS.md`) продолжает работать без изменений и на тех же ручках.
- **Векторный `crop.pdf` и его кэш** для блоков, нарезанных самим RD WEB
  (`services/web_ocr/crop/service.py:103`). Внешняя ветка его не заменяет и не отменяет — она рядом.
- **Агентский путь** (`/api/agent/v1`, выдача элементов работы, приём результата) остаётся как есть.
  Внешний кроп для агента неотличим от внутреннего: агент получает растр по ссылке и не знает, кто
  его нарезал.

## 3. Контекст (пункт 1)

**Что портал присылает.** Один HTTP-запрос = одна страница исходного комплекта = от одного до
шестнадцати кропов. Полностраничный лист A4 даёт один кроп типа `text`; крупный лист — кроп `stamp` и
один-два кропа `text` (зона номера листа). На эталонном комплекте 220 страниц это ≈230 кропов и
150–250 МБ трафика: полностраничные `text` кодируются в JPEG q=85, штампы и зоны номера — PNG без
потерь.

**Растр уже готов к модели.** Кроп нарезан из рабочего PDF при детерминированном DPI (300 при площади
страницы до 40 Мпикс, ниже — только для очень крупных листов), развёрнут по `content_rotation`
страницы (ADR-0020 портала) и ужат до потолка длинной стороны 3000 px для полностраничных блоков.
Канонический DPI кропа у RD WEB — тот же 300 (`services/web_ocr/core/settings_models_queue_provider.py:18`),
то есть масштабы сторон совпадают без пересчёта. Версия геометрической политики
(`crop_policy_version`) и версия кодирования (`encoding_policy_version`) едут в манифесте: по ним
портал отличает несовместимые прогоны, и они же позволяют RD WEB отказать, если политика ему
незнакома.

**PDF наружу не отдаётся.** Портал обязан обеспечить, чтобы исполнительная документация заказчика не
покидала контур целиком; блок — это фрагмент листа, документ — весь комплект. Поэтому у внешнего
блока не будет ни оригинального PDF, ни текстового слоя страницы, ни превью — и пункт 6 обязан
определить поведение фаз, которые сегодня на них рассчитывают.

**Дозапроса кропа нет ни у одной стороны.** На VLM-пути портала модель может попросить соседний
фрагмент; здесь такого механизма нет, и это осознанное ограничение: всё, что нужно модели, портал
отправляет сразу.

**Канал асимметричный.** Пишет портал по HTTP, читает — прямым `SELECT` из БД RD WEB под read-only
ролью. Причина: результат распознавания становится частью доказательной базы приёмки документации, и
портал обязан уметь доказать, что опубликованный текст получен ровно из той картинки, которую он
отправил. Соответствие «отправлено ↔ прочитано» держится на пяти инвариантах, и требования 3, 4, 5, 7
— ровно те из них, которые портал не может обеспечить у себя.

## 4. P0 — блокирует боевой запуск

### 4.1. Ветка внешнего кропа в конвейере (пункт 6)

**Сейчас.** Подготовка вызова провайдера начинается с безусловной загрузки трёх сущностей:
`get_block`, `get_document`, `get_job` (`services/web_ocr/pipeline/processor_prepare.py:66-68`).
Отсутствие любой из них — терминальный отказ или отмена (`:69-86`). Дальше так же безусловно
вызывается `self._crop.build_crop(scope, block)` (`:155`), который сам читает документ
(`services/web_ocr/crop/service.py:110`), сверяет `page_index` с `document.page_count` (`:111-112`),
режет вектор из оригинального PDF (`:180` — `_load_original_pdf`) и растеризует его в модельный PNG
(`:239-251`). Единственный S3-артефакт кропа — векторный `crop.pdf`
(`services/web_ocr/providers/contracts.py:75-77`); растр живёт в памяти.

От этого растра зависят ещё четыре места. Происхождение (`services/web_ocr/pipeline/lineage_record.py:93,98`)
считает ожидаемый хеш из `prepared.crop.image_bytes` и пишет в строку `source_pdf_sha256` документа
(`:117`). Приём результата умеет **отвергать сдачу** при расхождении этого хеша, если включена
пара флагов `queue.crop_lineage` (`services/web_ocr/api/services/agent_result.py:92-101`,
`services/web_ocr/core/settings_models_crop_lineage.py:90`). Preflight контекста считает бюджет
изображения по `crop.width_px/height_px` (`services/web_ocr/pipeline/processor_preflight.py:129`), а
при переполнении ужимает растр **перерастеризацией `crop.pdf`**
(`services/web_ocr/pipeline/processor_preflight.py:401` → `services/web_ocr/crop/service.py:262`).
Фаза 2 (refine) снова зовёт `build_crop(need_image=True)`
(`services/web_ocr/pipeline/refinement/processor_prepare.py:145`) и читает текстовый слой того же
`crop.pdf` (`services/web_ocr/pipeline/refinement/pdf_text_layer.py:143-167`).

Схема БД к этому присоединяется: `recognition_tasks.document_id` и `recognition_jobs.document_id`
объявлены `NOT NULL` (`services/web_ocr/database/postgres/schema/040_jobs_tasks.sql:9,41`), как и
`blocks.document_id` (`030_blocks_results.sql:9`) и `documents.s3_original_key`
(`020_tree_documents.sql:41`). Слова `external_id`, `external_batch_id` в исходниках RD WEB не
встречаются вовсе; `crop_source` встречается, но означает другое — чем кормится модель на агентском
узле, со значениями `''`, `local_shadow`, `local`
(`services/web_ocr/api/routes/_agent_schemas.py:199-201`).

**Цена.** Без этой ветки любая ручка приёма упирается в конвейер: задача внешнего блока падает на
`get_document` либо на `build_crop`, не дойдя до модели, и портал получает не текст, а `crop_not_ready`
на каждый кроп. Никакая аккуратность интегратора этого не компенсирует: подготовка исполняется внутри
RD WEB и снаружи не подменяется.

**Требуется.** Ветка «растр пришёл готовым» на всём пути исполнения блока. Минимальный набор точек:

1. **Контейнер вместо документа.** Внешний батч создаёт (идемпотентно) документ-контейнер в
   выделенном проекте портала: `file_name` = `external_batch_id`, `s3_original_key` — пусто или ключ
   заглушки, `page_count` — число страниц батча либо `NULL`. Альтернатива — снять `NOT NULL` с
   `document_id`, но это дороже: документ читают ещё превью, экспорт и верификатор. Контейнер честнее
   и не трогает ни одну существующую сверку.
2. **`build_crop` пропускается.** Признак внешнего блока (новая колонка `blocks`; имя на усмотрение
   команды, но **не** `crop_source` — оно занято другой осью, см. «Сейчас») переключает подготовку на
   чтение уже загруженных байтов по ключу объекта, сохранённому при приёме. Ни `get_document` ради
   PDF, ни проверка `page_index` против `page_count`, ни векторный рез при этом не выполняются.
3. **Происхождение строится из загруженных байтов.** `lineage_fields` получает те же байты, что уедут
   модели; `source_pdf_sha256` для внешнего блока пуст либо равен присланному `crop_sha256`. Сверка
   `queue.crop_lineage` не имеет права отвергать сдачу на том основании, что растр «чужой»: у
   внешнего блока другого растра не бывает.
4. **Preflight считает бюджет по присланным размерам.** `crop_width_px`/`crop_height_px` приходят в
   манифесте; ужатие при переполнении контекста выполняется перекодированием загруженного растра, а
   не перерастеризацией несуществующего `crop.pdf`.
5. **Фазы `refine` и `verify` определены.** Допустимы оба решения — деградация (зонд текстового слоя
   возвращает `crop_pdf_missing`, что уже предусмотрено, `pdf_text_layer.py:167`) или явное
   выключение Фазы 2 для внешних блоков. Недопустимо третье: падение с необъяснённой ошибкой.
   Портал в MVP Фазой 2 не пользуется и просит только определённости.
6. **Экспорт и удаление проекта определены.** Внешний батч не должен ломать `document_export` и
   `project_purge`; новая таблица приёма обязана быть внесена в `PURGED_TABLES` либо в `KEPT_TABLES` с
   причиной (`services/web_ocr/api/services/project_purge_tables.py:18,55`), иначе гард-тест каскада
   упадёт — и правильно сделает.

**Приёмка.** Сквозной тест через РЕАЛЬНЫЙ worker, а не через мок подготовки: `POST` внешнего кропа →
задача заклеймлена → модель вызвана → строка в `block_results` со `status='success'` → строка видна во
вью пункта 7. Отдельно: тот же тест на блоке типа `stamp` даёт `result_type='stamp_json'` и разбор в
`StampBlockResult`. Отдельно: `pytest` каскада удаления проекта (`services/web_ocr/tests/api/test_project_purge_tables.py`)
проходит на изменённой схеме.

### 4.2. Ручка приёма готового кропа (пункт 2)

**Сейчас.** Единственный вход растра в RD WEB — документ: `POST /api/documents/upload/init` выдаёт
presigned PUT на оригинальный PDF (`services/web_ocr/api/routes/documents_upload.py:55`),
`upload_complete` подтверждает загрузку (`:129`), дальше страницы рендерятся, а кропы режутся из PDF.
Все существующие crop-маршруты — на **отдачу**: `GET /api/blocks/{id}/crop-url` и `GET /api/blocks/{id}/crop`
(`services/web_ocr/api/routes/blocks_crop.py:28,58`), `GET /api/crops/{token}`
(`services/web_ocr/api/routes/crops.py:79`). Ручки, принимающей готовый растр блока, нет. Ближайший по
смыслу код — `services/web_ocr/central/guards.py`: это границы того, что RD WEB САМ отправляет в
центральный сервис разбора (allowlist `{"image/png"}` `:37`, потолок тела 12 МиБ `:41`, потолок
пикселей после декодирования 40 Мпикс `:45`), то есть исходящая сторона, а не входящая.

**Цена.** Без ручки нового пути нет вовсе: портал не может ни отдать растр, ни завести блок под него.
Обход единственный и неприемлемый — грузить в RD WEB рабочий PDF комплекта, чего портал делать не
имеет права (раздел 3).

**Требуется.** Версионированная ручка приёма батча кропов **одной страницы**; версионированная с
первого дня — прецедент уже есть у агентской поверхности (`/api/agent/v1`,
`services/web_ocr/api/routes/agent_enroll.py:41`).

```
POST /api/v1/external-crops/batch          Content-Type: multipart/form-data
```

Поля манифеста запроса (одна часть `manifest` типа `application/json`):

| Поле                | Смысл                                                                    |
| ------------------- | ------------------------------------------------------------------------ |
| `manifest_version`  | `"portal.crops.v1"`; незнакомое значение → 422                           |
| `project_id`        | Проект RD WEB, выделенный порталу                                        |
| `external_batch_id` | Идентификатор прогона распознавания на стороне портала                   |
| `selections`        | Выбор провайдера/модели/промпт-профиля по типам блоков присланных кропов |
| `crops[]`           | 1..16 записей, каждая соответствует одной части `file_*`                 |

Поля каждой записи `crops[]`:

| Поле                              | Смысл                                                                |
| --------------------------------- | -------------------------------------------------------------------- |
| `external_id`                     | Глобально уникальный id кропа; вычисляется порталом, не генерируется |
| `idempotency_key`                 | `sha256(external_id ':' crop_sha256)`                                |
| `block_type`                      | `text` / `stamp` — словарь RD WEB (`domain/enums.py:136-141`)        |
| `content_type`                    | `image/png` или `image/jpeg`                                         |
| `crop_sha256`                     | sha256 УХОДЯЩИХ байтов, hex в нижнем регистре                        |
| `crop_bytes`                      | Длина уходящих байтов                                                |
| `crop_width_px`, `crop_height_px` | Размеры растра                                                       |
| `page_index`, `sort_order`        | Позиция страницы и блока внутри неё                                  |
| `coords_norm`                     | Нормализованный bbox блока на странице (для UI и диагностики)        |
| `content_rotation`                | Уже применён к пикселям; ноль пишется явно                           |
| `crop_policy_version`             | Версия геометрической политики портала                               |
| `encoding_policy_version`         | Версия политики кодирования портала                                  |
| `render_dpi`                      | DPI растеризации страницы                                            |
| `page_width_px`, `page_height_px` | Размеры страницы при этом DPI                                        |
| `rasterizer`                      | Подпись растеризатора портала (вид и версия)                         |

Чего в манифесте НЕТ и быть не должно: имён файлов, имён объектов, ФИО, адресов, идентификаторов
ревизий разметки портала, текстов промптов, токенов. Кроп — фрагмент листа и метаданные о пикселях,
ничего больше.

Ответ **HTTP 200** с телом:

```json
{
  "accepted": [
    { "external_id": "…", "remote_block_id": "…", "remote_task_id": "…", "deduplicated": false }
  ],
  "rejected": [{ "external_id": "…", "code": "…", "message": "…" }]
}
```

Частичный успех — норма: `accepted` и `rejected` могут быть непусты одновременно, и это не ошибка
запроса. Коды HTTP, на которые портал реагирует по-разному, поэтому смешивать их нельзя:

| Код     | Когда                                                           | Что делает портал                       |
| ------- | --------------------------------------------------------------- | --------------------------------------- |
| 200     | Запрос разобран; исход каждого кропа — в теле                   | Штатная обработка `accepted`/`rejected` |
| 401/403 | Удостоверение неверно, отозвано или не даёт права на проект     | Останавливает весь прогон               |
| 409     | `external_id` уже принят с ДРУГИМ `idempotency_key`             | Помечает нарушение контракта            |
| 413     | Тело больше потолка                                             | Валит страницу, обход продолжается      |
| 415     | `content_type` вне allowlist                                    | Валит страницу                          |
| 422     | Манифест не разобран, незнакомая `manifest_version`, битые поля | Валит страницу                          |
| 429/5xx | Перегрузка, недоступность                                       | Повтор с backoff                        |

Лимиты объявляются явно и, желательно, читаемы ручкой `GET /api/v1/external-crops/limits` (прецедент —
`upload_limits`, `documents_upload.py:46`): максимум кропов в батче (портал шлёт до 16), максимум
байтов на кроп и на запрос, допустимые `content_type`. Портал не превышает 8 МиБ на кроп при JPEG
q=85 и просит потолок тела не ниже 32 МиБ; если ingress ограничен ниже — см. пункт 15.

Проверки входа делаются на границе, до декодирования — по образцу собственных `guards.py`: MIME из
allowlist, размер до декодирования, габариты из заголовка. Для JPEG понадобится разбор заголовка,
которого сегодня нет: `png_dimensions` (`central/guards.py`) читает только PNG.

**Приёмка.** Пробник интегратора (`pnpm rdcrop:probe`, раздел 9) отправляет два кропа, получает 200 с
двумя `accepted`; отправляет кроп с неверным `content_type` — получает 415; превышает потолок тела —
413; шлёт незнакомую `manifest_version` — 422 и ни одной строки в БД. В логах RD WEB ни при одном из
исходов не появляется содержимое манифеста целиком.

### 4.3. HTTP 200 = закоммиченная строка (пункт 3)

**Сейчас.** Утверждать нечего: ручки нет. Ближайший прецедент — приём результата от агента, где
идемпотентность выстроена двойная (кэш исхода по ключу плюс replay-ветка репозитория,
`services/web_ocr/api/services/agent_result.py:8-10`), то есть команда с этим классом требований
работает.

**Цена.** Если 200 будет означать «принято в обработку», портал теряет право считать отправку
состоявшейся: строки во вью ещё нет, повтор создаст вторую задачу, а решение «результата нет дольше
grace → переотправить новым id» будет срабатывать на здоровых кропах. Единственный обход —
искусственная задержка перед первым чтением, то есть догадка вместо контракта.

**Требуется.** Ответ 200 отдаётся ПОСЛЕ фиксации транзакции, создавшей задачу и её строку. Сразу
после получения 200 портал обязан увидеть строку во вью пункта 7 со `status='queued'`. То же для
`deduplicated: true`: повтор отвечает 200 только тогда, когда исходная строка существует и видна.

**Приёмка.** Тест: `POST` → немедленный `SELECT` из вью в отдельном соединении под read-only ролью →
строка есть, `status='queued'`, `crop_sha256` совпадает с отправленным. Тест выполняется без
`sleep`; повторный прогон с тем же телом даёт `deduplicated: true` и то же число строк.

### 4.4. `UNIQUE (external_id)` ограничением БД (пункт 4)

**Сейчас.** Уникальность в RD WEB обеспечивается ограничениями там, где она важна: PK
`(tenant_id, result_id)` у `block_results` (`030_blocks_results.sql:60`), PK `(tenant_id, task_id)` у
`recognition_tasks` (`040_jobs_tasks.sql:67`), детерминированный `task_id` из
`hash(job_id, block_id, block_version, …)` (`:38`). Поля `external_id` не существует, и уникальности
для него, соответственно, тоже.

**Цена.** Если уникальность будет обеспечена только кодом приёма, то две параллельные отправки одного
кропа (повтор после разрыва, две попытки задачи портала) создадут два блока и два результата на одну
картинку. Портал этого не заметит: во вью появятся две строки с одним `external_id`, и любая из них
может оказаться прочитанной. Публикация текста, полученного из второго распознавания той же картинки,
неотличима от публикации чужого текста — доказательность теряется целиком.

**Требуется.** `UNIQUE (external_id)` **ограничением в БД** на таблице приёма (или частичный
уникальный индекс, если поле живёт на `blocks`). Не «проверка перед вставкой», не «уникальность по
бизнес-логике»: гонка выигрывается только базой. Дедупликация по хэшу картинки при этом **запрещена**:
два разных `external_id` с одинаковыми байтами — законная ситуация (одинаковые пустые зоны номера на
двух листах), и портал обязан получить строку на каждый отправленный `external_id`.

**Приёмка.** `\d+` таблицы показывает уникальное ограничение. Тест: два конкурентных `POST` с одним
`external_id` и одним `idempotency_key` → одна строка, оба ответа 200, второй с `deduplicated: true`.
Тест: два `external_id` с идентичными байтами → две строки, оба распознаются.

### 4.5. Идемпотентность по `idempotency_key` (пункт 5)

**Сейчас.** У задач RD WEB `idempotency_key` есть и объявлен `NOT NULL`
(`040_jobs_tasks.sql:64`), пересчитывается репозиторием (`api/services/recognition.py:347`), и на нём
же держится replay-ветка приёма результата от агента (`api/services/agent_result.py:8-10`). Для
внешнего приёма ключа нет, потому что нет приёма.

**Цена.** Портал устроен так, что отправка кропа предшествует записи «отправлено»: сначала строка
леджера в состоянии `prepared` с отпечатком уходящих байтов, потом `POST`, потом отметка о приёме.
Разрыв между их 200 и нашей отметкой — штатный сценарий (перезапуск воркера, потеря аренды), и
единственный безопасный ответ на него — повтор. Без идемпотентности повтор создаёт второе
распознавание той же картинки; с идемпотентностью по хэшу картинки вместо ключа — теряет законный
второй кроп с теми же байтами.

**Требуется.** Три правила, ровно в такой формулировке:

1. Тот же `external_id` + тот же `idempotency_key` → **200**, `deduplicated: true`, и в
   `accepted[]` возвращаются **те же** `remote_block_id` и `remote_task_id`, что были отданы в первый
   раз. Новой задачи не создаётся, повторного распознавания не происходит.
2. Тот же `external_id` + ДРУГОЙ `idempotency_key` → **409** с кодом `external_id_conflict`. Портал
   никогда не отправляет две разные картинки под одним `external_id` (id вычисляется, а отпечаток
   проверяется до отправки), поэтому 409 для него — сигнал о нарушении контракта, а не штатная ветка.
   Тело ответа может быть минимальным: полный манифест принятого кропа в нём не нужен.
3. Дедупликация по `crop_sha256` или по перцептивному хэшу картинки **запрещена** (см. 4.4).

**Приёмка.** Тест: `POST` → обрыв соединения на стороне клиента после фиксации → повтор того же тела
→ 200, `deduplicated: true`, те же `remote_*`, одна строка во вью, одна задача в `recognition_tasks`.
Тест: тот же `external_id` с другим `idempotency_key` → 409 `external_id_conflict`, состояние БД не
изменилось.

### 4.6. Вью `portal_block_results_v1` (пункт 7)

**Сейчас.** В схеме RD WEB нет ни одной вью: `grep 'CREATE VIEW'` по
`services/web_ocr/database/postgres/schema/` не даёт совпадений. Результаты лежат в `block_results`
(`030_blocks_results.sql:34-61`) со статусами `success | suspicious | error | non_retriable`
(`domain/enums.py:168-172`) и типами `html | image_json | stamp_json | error` (`:175-179`); текст — в
`ocr_markdown` / `ocr_text` / `ocr_json` (`030_blocks_results.sql:45-48`). Наружу результаты отдаются
поштучно (`GET /api/blocks/{id}/results`) либо экспортом документа
(`services/web_ocr/api/routes/exports.py`).

**Цена.** Портал не имеет права читать таблицы RD WEB: их состав и семантика — внутреннее дело
принимающей команды, а чтение `block_results` напрямую сделало бы любую их миграцию поломкой
интеграции. Поштучный HTTP-опрос 230 блоков на комплект — это 230 запросов на каждый цикл поллинга,
и он всё равно не отвечает на вопрос «какие из МОИХ `external_id` уже готовы».

**Требуется.** Одна вью — единственная поверхность чтения, стабильная по составу колонок:

```sql
CREATE VIEW portal_block_results_v1 AS SELECT
  contract_version,          -- строковая версия контракта вью
  external_id,               -- ровно то, что прислал портал
  external_batch_id,
  remote_block_id, remote_task_id, result_id,
  block_type,
  crop_sha256,               -- ЭХО присланного значения, не пересчёт
  status,                    -- см. пункт 11
  result_type,
  ocr_markdown, ocr_text, ocr_json,
  model_id, prompt_profile_id, confidence, attempts, latency_ms,
  error_code, error_message,
  created_at, updated_at
FROM …;
```

Обязательные свойства:

- **Одна строка на `external_id`.** Не «последняя из нескольких», а одна — это следствие пункта 4.
- **`crop_sha256` — эхо присланного портала значения**, а не собственный хэш RD WEB. Внутренний
  `model_input_digest` считается по другой схеме (`contracts/crop_preprocess/v1/pixels.py:150-170`:
  домен-разделитель `rd.modelin.1`, длина перед данными, префикс `sha256:`) и с плоским sha256 не
  совпадает по построению. Портал сверяет эхо с отпечатком уходивших байтов при каждом чтении и при
  расхождении не публикует текст никогда.
- **Терминальная строка неизменна.** Достигнув терминального статуса, строка не меняет ни `status`,
  ни текст, ни `result_id`. Новый результат по тому же блоку (переразбор, ручная правка) — это новый
  `result_id`; портал такое изменение заметит и запишет в журнал, но опубликованное не тронет.
- **Индекс `(external_batch_id, external_id)`.** Портал делает два запроса на опрос: список
  `external_id` батча и строки по массиву ещё открытых id. Оба должны быть индексными.
- **`contract_version`** — чтобы портал отличал расширение вью от смены её смысла.

**Приёмка.** `SELECT` под ролью пункта 8 отдаёт все перечисленные колонки. Тест: после сквозного
прогона (4.1) `crop_sha256` во вью посимвольно равен отправленному; `EXPLAIN` обоих запросов портала
показывает использование индекса; повторное чтение терминальной строки через сутки даёт тот же
`result_id` и тот же текст.

### 4.7. Роль только для чтения (пункт 8)

**Сейчас.** Подключение к БД конфигурируется одним DSN (`services/web_ocr/db/dsn.py`), под которым
приложение и мигрирует схему, и пишет данные. Отдельной read-only роли, ограниченной вью, в
репозитории нет; `GRANT`-ов в файлах схемы (`database/postgres/schema/`) тоже нет.

**Цена.** Без выделенной роли единственный способ дать порталу читать — выдать ему учётные данные,
которыми можно и писать. Это ровно та ситуация, из-за которой в `docs/RDWEB_IMPROVEMENTS.md` пункт 1
стоит первым: запрет становится регламентным, а не техническим, и «портал ничего у вас не менял»
превращается в утверждение доверия вместо утверждения о правах.

**Требуется.** Роль `portal_reader` со следующими свойствами:

- `GRANT SELECT` **строго на вью** `portal_block_results_v1`; ни на одну таблицу прав нет, `USAGE` на
  схему выдан минимально необходимый;
- `CONNECTION LIMIT` (порталу достаточно 2 — столько соединений держит его пул читателя);
- `statement_timeout` и `idle_in_transaction_session_timeout` на роли, чтобы забытая транзакция
  портала не удерживала ресурсы;
- TLS обязателен, CA-сертификат передаётся порталу отдельно от пароля; порталу нужен `sslmode=verify-full`;
- сетевой allowlist по адресам портала;
- процедура ротации пароля с окном, согласованным заранее.

Портал со своей стороны ставит те же ограничения трижды: `SELECT` только на вью,
`BEGIN TRANSACTION READ ONLY` с `SET LOCAL statement_timeout` на каждый опрос и пул на 2 соединения.
Записи в БД RD WEB портал не делает ни при каком исходе — это инвариант его кода, а не намерение.

**Приёмка.** Под `portal_reader`: `SELECT` из вью работает; `SELECT` из `block_results` даёт
`permission denied`; `INSERT`/`UPDATE`/`DELETE`/`CREATE` в любой объект дают `permission denied`;
третье одновременное соединение отвергается лимитом; запрос длиннее `statement_timeout` снимается
сервером. Проверка выполняется тем же способом, каким портал ходит в боевую базу, и её вывод
прикладывается к приёмке.

## 5. P1 — снимает обход или закрывает риск

### 5.1. Служебное удостоверение для приёма (пункт 9)

**Сейчас.** Пользовательский вход — `POST /api/auth/login` с парой email/пароль, выдающий JWT
(`services/web_ocr/api/routes/auth.py`). Но с момента написания `docs/RDWEB_IMPROVEMENTS.md` в RD WEB
появился **машинный принципал**: агентский токен с собственным префиксом `rdagent_`
(`services/web_ocr/domain/models_agents.py:43`), хранимый только хэшем и жёстко привязанный к узлу
(`services/web_ocr/api/services/agent_auth.py:14-16`, `domain/models_agents.py:169`), с
протоколом регистрации по одноразовому коду (`services/web_ocr/api/routes/agent_enroll.py`) и
выпуском сертификатов (`api/routes/admin_agent_certificates.py`). То есть механизм для не-человека в
системе уже есть — просто он рассчитан на исполнителя, а не на поставщика работы.

**Цена.** Без своего удостоверения портал ходит в ручку приёма сессией служебного аккаунта, то есть
учётной записи, устроенной как человеческая: её пароль лежит в secret storage портала, ротация ручная
и требует согласованного окна, а в аудите RD WEB действие портала неотличимо от действия человека с
теми же правами. Отдельно неприятно, что отзыв доступа порталу — это блокировка учётной записи, у
которой нет контура, отдельного от людей.

**Требуется.** Токен службы с областью «только приём внешних кропов в указанные проекты», выпускаемый
и отзываемый администратором, хранимый хэшем, отличимый от JWT по префиксу — по образцу уже
работающего агентского механизма. До его появления MVP работает на **отдельном** служебном аккаунте:
не на том, которым пользуется легаси-интеграция портала, чтобы отзыв или ротация одного не роняли
второй путь.

**Приёмка.** Токен службы принимается ручкой 4.2 и отвергается всеми остальными ручками RD WEB;
отзыв токена даёт 401 на следующем же запросе; в `audit_events` действия портала отличимы от действий
людей по принципалу.

### 5.2. Таксономия статусов (пункт 11)

**Сейчас.** Терминальность задачи в RD WEB определена ровно один раз и намеренно вынесена в домен:
`TERMINAL_TASK_STATUSES = {success, failed, dead_letter, canceled}`
(`services/web_ocr/domain/task_terminal.py:44-51`), и в докстроке этого файла описано, чего стоило
расхождение двух прежних определений. Для результата блока такого документа нет: словарь
`BlockResultStatus` (`domain/enums.py:168-172`) перечисляет значения, но не говорит, какие из них
окончательны и какие могут смениться позже.

**Цена.** Портал вынужден вывести терминальность эмпирически. Он делает это так: `success` и
`suspicious` — потребить, `error` и `canceled` — ошибка блока, `non_retriable` — отказ, `queued` и
`running` — ждать. Если хоть одно из этих отнесений неверно, портал либо опубликует текст, который RD
WEB ещё собирался заменить, либо будет ждать вечно того, что уже никогда не придёт.

**Требуется.** Раздел документации (или комментарий к вью), отвечающий на три вопроса для каждого
значения `status` во вью: окончателен ли статус; может ли строка после него измениться и при каких
условиях; должен ли портал переотправлять кроп новым `external_id` или бесполезно. Отдельно —
подтверждение или опровержение того, что фазы `refine`/`verify` могут заменить `result_id` уже
терминальной строки (вопрос 7.3).

**Приёмка.** Документ существует и покрывает все значения `status`, которые вью может отдать. Тест
портала `reconcile` строится по этому документу, а не по наблюдениям.

### 5.3. Ретеншн строк батча (пункт 12)

**Сейчас.** Удаление проекта — безвозвратное: `block_results`, `blocks`, `recognition_jobs`,
`recognition_tasks`, `documents` перечислены в `PURGED_TABLES`
(`services/web_ocr/api/services/project_purge_tables.py:36-42`), а гард-тест каскада требует явной
классификации каждой таблицы схемы (`:1-11`). Автоматического удаления результатов по сроку в
исходниках не обнаружено; если оно есть на уровне эксплуатации, это вопрос 7.5.

**Цена.** Портал читает результаты асинхронно и может дочитывать их после собственного сбоя,
перезапуска или паузы очереди. Если строка исчезнет раньше, чем он её потребил, кроп будет выглядеть
как `result_missing`, и портал отправит его заново — лишний GPU-час на стороне RD WEB и лишние
полдня на стороне приёмки документации.

**Требуется.** Строки внешнего батча живут **не менее 30 суток** после достижения терминального
статуса. `project_purge` выделенного порталу проекта в норме не запускается; если он всё же
запускается, это согласованная операция, а не фоновая уборка. Требование распространяется и на новую
таблицу приёма: её классификация в каскаде должна быть осознанной и обоснованной в комментарии — это
как раз то, чего требует их собственное правило («не знаю, что с ней делать» недопустимо, `:10-11`).

**Приёмка.** Строка, ставшая терминальной 30 суток назад, читается вью. Гард-тест каскада проходит, и
в `PURGED_TABLES`/`KEPT_TABLES` для новой таблицы указана причина.

### 5.4. `raw_output_sha256` во вью (пункт 10)

**Сейчас.** Сырого ответа модели во вью нет и в `block_results` нет: хранятся разобранные
`ocr_markdown`/`ocr_text`/`ocr_json` (`030_blocks_results.sql:45-48`). Хэш сырого ответа в исходниках
не встречается.

**Цена.** Портал записывает в свой журнал прогонов `outputHash` — отпечаток того, что вернула модель.
На VLM-пути это хэш сырого ответа. Здесь сырого ответа нет, поэтому портал вычисляет **канонический**
хэш по колонкам вью (`ocr_markdown`, `ocr_text`, `ocr_json`, `result_type`, `model_id`). Это рабочее
решение, но оно отвечает на вопрос «изменилось ли то, что мы прочитали», а не «изменилось ли то, что
сказала модель»: переформатирование при разборе на стороне RD WEB останется незамеченным.

**Требуется.** Колонка `raw_output_sha256` во вью — хэш сырого текста ответа модели до разбора, если
RD WEB его считает или может посчитать. Хранить сам текст не требуется.

**Приёмка.** Колонка присутствует; для двух прогонов одного кропа с идентичным ответом модели значения
совпадают. Если поле отдаётся, портал кладёт его в структурированный результат рядом со своим
каноническим хэшем — не заменяя его.

### 5.5. Наблюдаемость во вью (пункт 13)

**Сейчас.** `block_results` хранит `model_id`, `prompt_profile_id`, `confidence`, `provider_type`,
`provider_endpoint_id`, `meta` (`030_blocks_results.sql:51-57`); число попыток живёт на задаче
(`recognition_tasks.attempts`, `040_jobs_tasks.sql:57`), тайминги — в попытках (`task_attempts`).
Наружу интегратору ничего из этого не отдаётся одним запросом.

**Цена.** Когда качество распознавания падает, портал видит только текст. Отличить «модель сменилась»
от «промпт-профиль сменился» от «кроп ушёл на третью попытку и деградировал» он не может и вынужден
просить принимающую команду посмотреть в свою админку — то есть переводить техническую диагностику в
переписку.

**Требуется.** Колонки `attempts`, `latency_ms`, `model_id`, `prompt_profile_id`, `confidence` во вью
пункта 7 (они уже перечислены там). Отдельного API не нужно — вью достаточно.

**Приёмка.** Значения непусты для успешных строк и согласуются с тем, что показывает админка RD WEB
для того же блока.

### 5.6. Правило неизвестных полей (пункт 14)

**Сейчас.** Прецедент терпимости к лишним полям в RD WEB есть: `QaManifest` объявлен с
`extra="allow"` и явным комментарием, что дополнительные свойства не запрещаются
(`services/web_ocr/domain/results.py:192-194`). Общего правила для контракта приёма, разумеется, пока
нет.

**Цена.** Без правила любое расширение манифеста порталом требует согласованного окна выката с обеих
сторон: портал не может добавить поле, пока RD WEB его не знает, а RD WEB не может выкатить знание о
поле, пока портал его не шлёт. Это взаимная блокировка на ровном месте.

**Требуется.** Ручка приёма **игнорирует** неизвестные ключи манифеста, а не отвергает запрос. Вью
может приобретать новые колонки — портал читает их по имени и лишние не мешают. Ломающее изменение
(смена смысла или типа существующего поля, удаление колонки) выкатывается **параллельной** версией:
`portal.crops.v2` для манифеста и `portal_block_results_v2` для вью, при этом v1 живёт до
согласованного отключения. Смена `contract_version` без смены имени вью означает только совместимое
расширение.

**Приёмка.** Запрос с лишним ключом в манифесте принимается штатно. Тест портала на чтение вью не
падает при добавлении в неё новой колонки.

## 6. P2 — оптимизация

### 6.1. Presigned-загрузка и уведомление (пункт 15)

**Сейчас.** Для больших объектов у RD WEB уже есть правильный паттерн: оригинальный PDF не идёт через
API, а грузится клиентом напрямую в S3 по presigned PUT (`api/routes/documents_upload.py:55-124`), и
потолок такого объекта — 500 МБ (`core/settings_models_runtime.py:145`), то есть на порядки больше
любого разумного потолка тела запроса. Уведомлений о готовности результата наружу нет: события
транслируются в WebSocket проекта (`api/routes/events.py`, `app.py:348`), который рассчитан на UI, а
не на сервер интегратора.

**Цена.** Небольшая, и потому пункт P2. Полностраничный JPEG q=85 листа A4 при 300 dpi занимает
единицы мегабайт, батч страницы — до 8–10 МиБ; это проходит обычным телом запроса. Поллинг вью
стоит порталу двух индексных запросов раз в несколько секунд на один активный прогон.

**Требуется.** Два независимых улучшения, каждое — только если понадобится. Первое: если потолок
ingress окажется ниже 8 МиБ (вопрос 7.1), выдавать presigned PUT на растр по образцу
`upload/init`, а в манифесте присылать ключи объектов вместо частей multipart. Второе: сигнал о
достижении терминального статуса — подписанный вебхук на адрес портала либо `LISTEN/NOTIFY` на канал,
доступный read-only роли. Портал в обоих случаях сохраняет поллинг как основной механизм: уведомление
сокращает задержку, но не может быть единственным источником истины.

**Приёмка.** Не назначается: пункт активируется отдельным решением.

## 7. Вопросы к принимающей команде

Ответы на них меняют не требования, а параметры, поэтому они собраны отдельно и не блокируют начало
работ.

1. **Потолок тела запроса на ingress.** Какой размер тела проходит до FastAPI на боевом контуре?
   Конфигурации обратного прокси в репозитории RD WEB нет (файлов `*.conf` не обнаружено), поэтому
   потолок известен только эксплуатации. От ответа зависит, нужен ли пункт 15.
2. **`crop_model_dpi` на готовых кропах.** Настройка `crop_model_dpi: 300`
   (`core/settings_models_queue_provider.py:18`, `settings.yaml:1626`) описывает, с каким DPI RD WEB
   растеризует СВОЙ кроп. Для внешнего растра она смысла не имеет. Подтвердите, что на внешней ветке
   она не применяется и не вызывает перерастеризацию.
3. **Меняют ли `refine`/`verify` `result_id` терминальной строки?** Фаза 2 создаёт новую ревизию
   результата (`block_results.result_phase`, `source_result_id`, `is_final`,
   `030_blocks_results.sql:41-43`). Портал обязан знать, увидит ли он смену `result_id` уже
   потреблённой строки — и, если да, при каких настройках job'а.
4. **Деградация качества на JPEG q=85.** Портал кодирует полностраничные `text`-кропы в JPEG ради
   трафика (150–250 МБ на комплект против 1–2.5 ГБ в PNG); штампы и зоны номера остаются PNG. Есть ли
   у команды RD WEB замеры влияния JPEG-артефактов на chandra-2 на мелком тексте? Если да, порог
   портала (`RDCROP_JPEG_THRESHOLD_BYTES`) будет выставлен по ним, а не по объёму.
5. **Автоматическая уборка результатов по сроку.** В исходниках она не обнаружена, но может
   существовать на уровне эксплуатации (cron, политика жизненного цикла бакета). Если существует —
   каков срок, и распространяется ли он на строки внешнего батча (пункт 12)?
6. **Имя признака внешнего блока.** Портал в своих документах называет ветку `crop_source='external'`,
   но `crop_source` в RD WEB уже занят другой осью — чем кормится модель на агентском узле
   (`api/routes/_agent_schemas.py:199-201`). Имя колонки выбирает принимающая команда; портал просит
   лишь, чтобы это были два разных имени.
7. **Границы для JPEG.** `central/guards.py` умеет читать габариты из заголовка только для PNG
   (`png_dimensions`). Готова ли команда добавить разбор заголовка JPEG на входящей границе, или
   порталу ограничиться PNG и заплатить трафиком?

## 8. Что портал гарантирует со своей стороны

Симметрично требованиям — чтобы принимающая команда знала, на что может опираться.

- `external_id` **вычисляется**, а не генерируется: `{runId}:{layoutBlockId}:r{round}`. Повтор задачи,
  потеря аренды и перезапуск воркера дают тот же `external_id`.
- Портал **никогда** не отправляет две разные картинки под одним `external_id`. Отпечаток уходящих
  байтов записывается в леджер до отправки и сверяется перед ней; при несовпадении отправки не
  происходит вовсе.
- Портал **никогда** не пишет в БД RD WEB и не читает её таблиц — только вью пункта 7, только
  `SELECT`, только внутри `BEGIN TRANSACTION READ ONLY`.
- Портал не публикует текст, у которого эхо `crop_sha256` разошлось с отпечатком отправленного
  растра, — ни при каком статусе и ни при каком числе попыток.
- Портал держит не более двух соединений к БД RD WEB и не более одного активного опроса на прогон.
- В журналы и в полезную нагрузку задач портала не попадают ни пароли, ни токены, ни имена файлов
  комплекта.

## 9. Приёмка и пробник

Приёмка проводится на **отдельном проекте** RD WEB, заведённом под интеграцию, и не затрагивает ни
один проект с боевыми данными.

Пробник интегратора — команда `pnpm rdcrop:probe` на стороне портала. Она выполняет один сквозной
цикл и печатает результат каждого шага:

1. `POST` одного кропа `text` и одного кропа `stamp` в ручку 4.2 → ожидается 200 с двумя `accepted`;
2. немедленный `SELECT` из вью под ролью `portal_reader` → ожидаются две строки со `status='queued'`;
3. опрос вью до терминального статуса → ожидается `success` на обеих строках;
4. сверка эха: `crop_sha256` во вью посимвольно равен отправленному → ожидается совпадение;
5. разбор: `text` даёт непустой `ocr_markdown`, `stamp` даёт `ocr_json`, разбираемый в
   `StampBlockResult`;
6. повтор шага 1 тем же телом → ожидается `deduplicated: true` и те же `remote_*`;
7. попытка `INSERT` под `portal_reader` → ожидается `permission denied`.

Пункт считается закрытым, когда пробник проходит все семь шагов на боевом контуре RD WEB, а сквозной
тест ветки (4.1) проходит в CI принимающей команды.
